## 文件概览

这个文件把"当前构建认识哪些事件类型"固化成一个运行时可查的 `Set<string>`。它导出两个常量：

- `KNOWN_SESSION_EVENT_TYPES`：本仓库声明的**全部** `SessionEventMap` 成员——core 事件与各插件 declaration-merge 进来的事件（`compaction/*`、`hook/*`、`approval/*`、`todo/write`、`team/*` 等）都在其中。由 `gen-persistence-catalog.ts` 扫描类型声明生成，`pnpm run verify-persistence-catalog`（`doc-sync` 的一部分）保证不陈旧。
- `MESSAGE_PROJECTION_EVENT_TYPES`：模型可见效果需要**显式纯解释器**的事件类型（当前只有 `image/offload`）。

角色：它是 required-on-read 约定在**读取路径**上的执行依据——`surface.ts` 的 `surfaceOpOf()` 用它区分"本构建已知的 log-only 事件"与"未知的 ignorable 记录"。

## 关键代码走读

### 1. 已知类型集合（节选）

```typescript
/**
 * Every `SessionEventMap` member declared in this repository — the event
 * vocabulary this build understands. The persistence read path refuses to
 * interpret a log containing a type outside this set unless the event
 * carries the envelope's `ignorable` marker (see `SessionEvent.ignorable`
 * in `./types.ts`): such a log was likely written by a newer harness, and
 * silently skipping a required event would reconstruct a wrong session.
 * Downstream (out-of-repo) plugin events are outside this list by
 * construction. The persisted `SessionEvent.ignorable` marker is the
 * compatibility mechanism; event-name registration was rejected because
 * it does not classify omission safety and would make reads
 * composition-dependent. The rationale is in
 * `.agents/notes/implemented/architecture/2026-08-30-retain-ignorable-external-session-events.md`.
 */
export const KNOWN_SESSION_EVENT_TYPES: ReadonlySet<string> = new Set([
  'agent-preset/selected',
  'agent/inbox/spliced',
  'approval/asked',
  'approval/decided',
  'approval/policy',
  'assistant/attempt',
  'assistant/message',
  'command/done',
  'command/run',
  'compaction/end',
  'compaction/prune',
  'compaction/start',
  'compaction/summary',
  // …（共 63 个成员，覆盖 turn/*、step/*、user/system/developer/assistant/message、
  //    tool/*、request/*、session/end-seed、session/title、feedback/*、goal/*、
  //    hook/*、image/offload、job/*、llm/retry*、model/selection、plan/mode、
  //    sandbox/mode、schedule/*、subagent/*、team/*、todo/write、tool-workflow/*、
  //    working-directory/change、workspace/changes 等）
  'turn/end',
  'turn/start',
  'user/message',
  'web/deepseek-search-llm-request',
  'working-directory/change',
  'workspace/changes',
])
```

三个要点：

1. **`ReadonlySet<string>` 而不是类型收窄**：插件 merge 进来的类型在编译期属于 `SessionEventType`，但运行时读取（restore、fold）拿到的是 JSON 数据，需要一个字符串级"认识/不认识"的判据。
2. **列表不含仓外插件事件**：下游（本仓库之外）插件的事件天然不在列表里——它们必须自带 `ignorable: true` 才能被本构建读取。
3. **兼容机制的选型理由写在 JSDoc 里**：曾考虑过"事件名注册"机制但被否决，因为它无法分类"缺失是否安全"，且会让读取结果依赖插件组合（composition-dependent）。持久化在信封上的 `ignorable` 标记才是兼容机制——它由写入方逐事件声明，读取方按事件独立决策。

### 2. 消息投影事件类型

```typescript
/** Event types whose model-visible effects require an explicit pure interpreter. */
export const MESSAGE_PROJECTION_EVENT_TYPES: ReadonlySet<string> = new Set([
  'image/offload',
])
```

`image/offload`（由 `dsh-compaction-image-offload` 声明）会**改变已有消息的内容**（把消息里的图片块替换为附件引用）。这类事件与普通 log-only 事件不同：没有解释器就无法正确派生模型历史。`surface.ts` 的 `planSurfaceEvent` 在遇到此集合中的类型而无已注册投影定义时直接抛错——append、restore、fold 三条路径都会拒绝，宁可失败也不猜测。

## 与其他模块的关系

- **生成器 `scripts/gen-persistence-catalog.ts`**：扫描 `SessionEventMap` 的 declaration-merge 声明生成此文件；`docs/persistence-catalog.md`（持久化事件目录）由同一生成器产出，两者保持一致。

- **实验性插件记录**：`plugin:<owner>/<record>` 类型**永远不进入**本集合（它们不是 `SessionEventMap` 成员），靠信封上的 `ignorable: true` 与 `plugin:` 语法（`types.ts` 的 `PluginRecordType`）识别。

## 小结

`known-event-types.ts` 是"required-on-read"从类型声明到运行时判据的桥梁：读取方拿到的永远是 JSON 字符串，而这张生成清单让"这个构建是否认识该类型"成为一次 `Set.has()` 查询。它体现了模块的一条兼容性原则——**识别靠随事件持久化的标记（`ignorable`），不靠全局注册表**，这样读取行为不会因为部署里装了哪些插件而改变。
